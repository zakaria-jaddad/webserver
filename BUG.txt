BUG-001: POST handler always returns 500 Internal Server Error
------------------------------------------------------------------------------
Violated requirement:
  subject.md: "You need at least the GET, POST, and DELETE methods" and
  "Clients must be able to upload files".

Steps to reproduce:
  1. Start the server with conf/test.conf.
  2. Send any POST request, e.g.:
     POST /uploads HTTP/1.1
     Host: localhost
     Content-Type: application/x-www-form-urlencoded
     Content-Length: 9

     name=value

Expected behavior:
  POST should be processed. For a route with an upload_store, a successful
  upload/form submission should return 200/201/204. For malformed requests
  the server should return 400 or 411, not 500.

Actual behavior:
  The server responds with HTTP/1.1 500 Internal Server Error for every POST
  request, including those with valid Content-Length, chunked encoding, or
  multipart/form-data bodies.

Severity: Critical

  test/test_request_parsing.py::TestBodyParsing::test_malformed_chunk_size
  test/test_http_methods.py::TestPost::test_post_urlencoded

BUG-003: Oversized request body causes connection reset / server crash
------------------------------------------------------------------------------
Violated requirement:
  subject.md: "Set the maximum allowed size for client request bodies" and
  "Your program must not crash under any circumstances".

Steps to reproduce:
  1. Start the server with conf/test.conf (client_max_body_size 10m).
  2. Send a POST request whose body is larger than 10 MiB:
     POST /uploads HTTP/1.1
     Host: localhost
     Content-Type: application/octet-stream
     Content-Length: 11534336

     <11 MiB of data>

Expected behavior:
  HTTP/1.1 413 Payload Too Large and the connection stays alive.

Actual behavior:
  The server resets the TCP connection (ConnectionResetError) while the body
  is still being sent. This indicates the server process crashed or forcibly
  closed the socket instead of sending a 413 response.

Severity: Critical
Exposed by:
  test/test_request_parsing.py::TestBodyParsing::test_oversized_body

BUG-004: Server does not reject / report invalid configuration files
------------------------------------------------------------------------------
Violated requirement:
  subject.md: "Your program must use a configuration file, provided as an
  argument on the command line, or available in a default path."

Steps to reproduce:
  1. Run ./ft_webserver with an empty file:
     ./ft_webserver /dev/null
  2. Run ./ft_webserver with an invalid listen directive:
     echo 'server { listen not_a_port; root ./www; }' > /tmp/bad.conf
     ./ft_webserver /tmp/bad.conf
  3. Run ./ft_webserver with a server block that has no root:
     echo 'server { listen 127.0.0.1:2090; }' > /tmp/bad.conf
     ./ft_webserver /tmp/bad.conf

Expected behavior:
  The server should detect the invalid/missing configuration and exit with a
  non-zero status code (or at least print a clear error).

Actual behavior:
  - Empty config: server stays running but never listens on any port.
  - Invalid listen: server exits with status code 0, silently ignoring the
    error.
  - Missing root: server stays running with an empty root path.

Severity: Medium
Exposed by:
  test/test_config.py::TestConfigurationErrors::test_missing_config_file
  test/test_config.py::TestConfigurationErrors::test_invalid_listen_directive
  test/test_config.py::TestConfigurationErrors::test_missing_root

BUG-006: CGI responses emit an extra CRLF before the first chunk
------------------------------------------------------------------------------
Violated requirement:
  subject.md: "Execution of CGI..."; RFC-aligned chunked encoding.

Steps to reproduce:
  1. Start the server with conf/test.conf.
  2. Request a CGI script:
     GET /cgi-bin/test.php HTTP/1.1
     Host: localhost
  3. Inspect the raw bytes after the response headers.

Expected behavior:
  Chunked body begins immediately with the first chunk-size line.

Actual behavior:
  The chunked body starts with an extra \r\n before the first chunk size
  (e.g. "Transfer-Encoding: chunked\r\n\r\n\r\n79a\r\n..."). Strict chunked
  decoders will fail to parse the body. The test suite decoder has been made
  tolerant of this to allow further CGI verification.

Severity: Medium
Exposed by:
  test/test_cgi.py (mitigated by tolerant decoder in test/helpers.py)

BUG-007: POST handler treats status 200 as an error page lookup
------------------------------------------------------------------------------
Violated requirement:
  subject.md: "Your HTTP response status codes must be accurate".

Steps to reproduce:
  See BUG-001; any POST request triggers Response::servePages(200, ...).

Expected behavior:
  A 200 response should be generated directly for a successful POST, or the
  correct error code for malformed input.

Actual behavior:
  Response::httpPost calls servePages(200, 0). servePages treats 200 as an
  error status and looks it up in the error_pages map. If the entry is missing
  it returns 500, which is why all POST requests currently produce 500.

Severity: High
Exposed by:
  All POST-related tests listed under BUG-001.

BUG-008: Static error-page file descriptor is shared globally
------------------------------------------------------------------------------
Violated requirement:
  subject.md: "Stress test your server to ensure it remains available at all
  times" and "properly handle client disconnections".

Steps to reproduce:
  See src/response/ResponseUtilities.cpp servePages(int code, bool): the
  variable "static int fd = -1" is shared across all Response instances and
  therefore across all concurrent clients.

Expected behavior:
  Each response should open and close its own error-page file descriptor.

Actual behavior:
  A single static fd is reused. Under concurrency or rapid sequential error
  responses the wrong error page may be served, file offsets may be corrupted,
  or fd leaks may occur.

Severity: High
Exposed by:
  Potentially any error-page test; most visible under stress/concurrency.
  test/test_connections.py::TestSimultaneousClients::test_ten_concurrent_clients
  test/test_connections.py::TestStress::test_rapid_sequential_requests
